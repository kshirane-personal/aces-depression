        │
        │  ① ACEモジュールを実施した13州・地域だけ残す
        │  ② ACEモジュールに回答した人だけ残す

   統合データ 60,491件 × 299変数
        │  内訳: メイン 39,283 / V1 14,576 / V2 6,632
        │
        │  ③ 研究で使う58列だけに絞る

行数は最初から最後まで 60,491 のまま変わらない。**レコードを削除するのではなく、
使えない値を欠損（NaN）にしていく**設計になっている。実際に何件使えるかは、
どの変数を必要とするかによって後から決まる。

| 条件 | 使える件数 |
|---|---|
| 統合後の全レコード | 60,491 |
| うつ病診断歴（ADDEPEV3）が有効 | 60,166（99.5%） |
| ACEスコアが有効 | 55,065（91.0%） |
| **主解析の実効サンプル**（上記2つ＋事前指定した予防医療2変数） | **54,105（89.4%）** |

この表は前処理を実行するたびに `data/interim/sample_flow.md` に自動で書き出される。

学会発表でサンプルサイズを聞かれたらこのファイルを見れば足りる。

## ステップ①②③: 3つのファイルを1つに統合する

担当: `src/data_loader.py`

### やっていること

BRFSSは全米調査だが、ACEモジュールは**州が任意で採用する追加モジュール**なので、
実施した州のデータしか使えない。さらに実施州の中でも、メインファイルに入っている州と、
Version 1 / Version 2 という別ファイルに入っている州がある。

そこで3ファイルそれぞれについて、

1. ACEモジュール実施州のレコードだけ抜き出す
2. ACEモジュールに回答した人だけ残す
3. どのファイル由来かを `_SOURCE` 列に記録する
4. ウェイト変数の名前を `_FINALWT` に統一する

をやってから、縦に積み重ねて1つの表にする。

### なぜウェイトの名前を統一するのか

BRFSSは複雑な標本設計なので、集計には必ずウェイト（重み）を使う。ところがウェイトの
変数名がファイルごとに違う。

| ファイル | ウェイト変数名 |
|---|---|
| メイン | `_LLCPWT` |
| Version 1 | `_LCPWTV1` |
| Version 2 | `_LCPWTV2` |

統合後にこれらを使い分けるのは事故のもとなので、読み込み時点で `_FINALWT` という
共通の名前にコピーしている。**分析では常に `_FINALWT` だけを使う。**

なお `_LLCPWT` はメインファイルにしか存在しないため、3ファイルの共通列を取る際に
統合データからは消える。これは想定通りの挙動。

### 埋め込まれている判断

- **「ACEモジュールに回答した人」の判定は `ACEDEPRS`（モジュール冒頭の設問）が
  欠損でないことで行う。** 「ACE項目のいずれかに回答」という緩い条件にしても
  拾える人数は1件しか増えなかったため、シンプルな条件を採用している
- **3ファイルは横に結合（マージ）せず、縦に積む。** 同一人物が複数ファイルに
  登場することはないため

### 注意点

メインデータのファイル名は `LLCP2024.XPT ` と**末尾にスペースがある**。CDCが配布している
原本がそうなっているため。パスは必ず `config.MAIN_DATA` 経由で参照する。

**V1 / V2 ファイルは MAIN の部分集合**。実際に確認したところ、V1の62,629件・V2の58,806件は
すべてMAINにも含まれていた（`SEQNO` + `_STATE` で照合）。したがって3ファイルのレコード数を
足すと二重計上になる。BRFSS 2024 の総回答者は **457,670件**であって579,105件ではない。

本研究が各ファイルから抽出する州は互いに素（MAIN: FL/GA/HI/NV/ND/VA/PR/USVI、
V1: IA/ME/OH、V2: AZ/OK）なので、**ACE回答者60,491件に重複はない**。

## ステップ④: 回答コードを解析用の値に翻訳する

担当: `src/preprocess.py` の `recode_outcomes` / `recode_ace_variables` / `recode_preventive_care`

### やっていること

BRFSSの回答は数字コードで入っている。そのままでは計算に使えないので翻訳する。

```
うつ病診断歴 ADDEPEV3
  1 = はい        → 1
  2 = いいえ      → 0
  7 = わからない  → 欠損
  9 = 回答拒否    → 欠損

メンタル不良日数 MENTHLTH
  1-30 = 日数     → そのまま
  88   = 0日      → 0     ← 「なし」を88で表す仕様
  77/99           → 欠損
```

**7・9・77・99 は「わからない/回答拒否」を表す特殊コードであり、データとしては欠損**。
これを数値のまま計算に混ぜると、77日間メンタル不良だったことになってしまう。

アウトカムは3本ある。`_MENT14D` は `MENTHLTH` から CDC が算出した3区分で、
**生涯診断ではなく現在の症状**を捉えるため、検出バイアスの評価に使う。

| 変数 | 内容 | 位置づけ |
|---|---|---|
| `ADDEPEV3` | うつ病の診断歴（生涯） | 主アウトカム |
| `MENTHLTH` | 過去30日のメンタル不良日数 | 副次アウトカム |
| `_MENT14D` | 上記の3区分（0日 / 1-13日 / 14日以上、9=欠損） | 頑健性確認 |

当初は PHQ-8 を使う計画だったが、BRFSS 2024 には収録されていないことを確認した
（全306変数を探索）。

ACE項目は質問形式によって翻訳ルールが3種類ある。

| 種類 | 項目数 | 回答形式 | 翻訳 |
|---|---|---|---|
| 家庭内の機能不全 | 5 | はい / いいえ | はい→1 |
| 虐待・DV目撃 | 6 | なし / 1回 / 2回以上 | **1回以上→1** |
| ネグレクト | 2 | 全くない〜いつも（5段階） | **逆転**。頻度が低いほど該当 |

### 埋め込まれている判断

- **虐待の頻度項目は「1回でもあれば該当」とする。** CDCの手順書・MMWR論文とも同じ扱い
- **ネグレクト2項目は逆転項目。** 「安全だと感じた頻度」を聞いているので、
  「全くない/たまに/ときどき」を該当、「ほとんど/いつも」を非該当としている
- **欠損は `None` ではなく `np.nan` で表す。** `None` を使うと列の型が壊れて
  平均値の計算などで問題が出るため（実際に一度そうなっていた）

## ステップ⑤: ACEスコアを組み立てる

担当: `src/preprocess.py` の `compute_ace_categories` / `compute_ace_score`

### やっていること

13個のACE質問項目のうち11項目を、**8つのカテゴリ**にまとめてから合計する。

```
11の質問項目                      8カテゴリ            スコア
─────────────────────────────────────────────────────────
ACESWEAR  ────────────────────→ 精神的虐待      ┐
ACEHURT1  ────────────────────→ 身体的虐待      │
ACETOUCH ┐                                      │
ACETTHEM ├──「いずれか該当」──→ 性的虐待        │
ACEHVSEX ┘                                      ├→ 合計（0-8点）
ACEDEPRS  ────────────────────→ 家庭内の精神疾患 │
ACEDRINK ┐                                      │
ACEDRUGS ┘──「いずれか該当」──→ 家庭内の物質依存 │
ACEPUNCH  ────────────────────→ DV目撃          │
ACEDIVRC  ────────────────────→ 親の離婚・別居  │
ACEPRISN  ────────────────────→ 家族の収監      ┘
```

複数項目を束ねるカテゴリ（性的虐待・物質依存）では、**どれか1つでも該当すれば
そのカテゴリは1点**。3回被害を受けても1点。これは「何種類の逆境を経験したか」を
測る指標だから。

### 混同しやすい2つの変数

| 変数 | 内容 | カテゴリ |
|---|---|---|
| `ACEPUNCH` | 親や同居の大人**同士**が殴り合った頻度 | DV目撃 |
| `ACEHURT1` | 子ども**自身**が大人に殴られた頻度 | 身体的虐待 |

「誰が誰に暴力をふるったか」が違う。過去に一度取り違えがあった箇所。

### 埋め込まれている判断

- **8カテゴリ全部が揃っていない人はスコアを欠損にする。** 1つでも欠ければ合計しない。
  CDCのMMWR論文も同じ方式（"Participants with missing data for any type of ACE were excluded"）
- **`ACEDIVRC` の「両親が未婚」（値8）は欠損として扱う。**
  これはCDCの2つの文書で見解が分かれている箇所で、MMWR 2023は欠損、
  2021年の手順書は「該当なし(0)」としている。本研究はMMWRに合わせた（該当790件）
- **ネグレクト2項目はスコアに含めない。** 5段階の頻度をどこで区切るかが恣意的で、
  「ときどき」を含めるか否かで該当率が12.6%から4.3%まで3倍動くため。
  CDCの2文書もどちらも8カテゴリで、ネグレクトを含めていない

### 3種類のスコアがある理由

主解析用に1本、感度分析用に2本を**あらかじめ**用意している。結果を見てから定義を
選ぶと「都合の良い結果に合わせた」ことになってしまうため、先に全部決めてある。

| 列名 | 定義 | 用途 |
|---|---|---|
| `ace_score` / `ace_group` | 8カテゴリ（0-8点） | **主解析** |
| `ace_score_ext` / `ace_group_ext` | 10カテゴリ（ネグレクト追加、0-10点） | 感度分析 |
| `ace_score_divrc8` / `ace_group_divrc8` | 8カテゴリ（両親未婚を0扱い） | 感度分析 |

層別化はどれも共通で **0 / 1 / 2-3 / 4以上** の4群。これはCDCのMMWR論文と同じ区切りで、
「4以上」を上限にしているのは、4以上の曝露と健康への悪影響を結びつける研究の蓄積が
あるため（MMWRがそう明記している）。

## ステップ⑥: 共変量の欠損コードを処理する

担当: `src/preprocess.py` の `clean_covariates`

### やっていること

年齢・人種・収入などの共変量にも「わからない/回答拒否」のコードが入っている。
**どの値が欠損コードかは変数ごとに違う**ため、`config.py` に変数名と欠損コードの
対応表を持っている。

特に間違えやすいのが年齢。

```
_AGEG5YR（5歳刻みの年齢）
  1  = 18-24歳
  ...
  13 = 80歳以上     ← 最高齢カテゴリはここ
  14 = わからない/回答拒否/欠損   ← 年齢ではない
```

14を「85歳以上」だと誤解すると、年齢不明の924人が最高齢層として集計される。
実際に一度そうなっていた。

### 共変量の3分類

登録漏れを防ぐため、共変量27個を必ず3つのどれかに分類している。

| 分類 | 変数数 | 意味 |
|---|---|---|
| 欠損コードあり | 22 | 対応表に登録して欠損化する |
| 欠損コードなし | 4 | そもそも特殊コードが無い（性別・BMIなど） |
| 個別処理 | 1 | `PHYSHLTH` は日数型なので別扱い |

`validate_data.py` が、どれにも属さない変数がないかを毎回チェックする。
分類し忘れた変数があれば警告が出る。**アウトカム3変数も同じ仕組みで検証している。**

この検証範囲は当初は共変量だけだった。`_MENT14D` を追加した際に欠損コード（9）の
登録を忘れ、しかも検証対象外だったため検出されなかったことがある。

## 検証: 何をチェックしているか

担当: `src/validate_data.py`（`python -m src.validate_data` で単体実行できる）

| # | チェック内容 |
|---|---|
| 0 | 共変量とアウトカムの欠損コード登録漏れがないか |
| 1 | レコード数とソース別の内訳 |
| 2 | 州別のレコード数、想定外の州コードが混ざっていないか |
| 3 | 変数ごとの欠損率と、閾値による分類 |
| 4 | アウトカム変数の分布 |
| 5 | ACE変数の分布 |
| 6 | サーベイウェイトの範囲と、0以下の異常値 |

### 欠損率について注意すること

チェック3の欠損率は、**欠損コードを処理した後**の値で判定している。生データのままだと
7や9が「有効な値」に見えてしまい、実態と大きくずれる。

```
_INCOMG1（世帯収入）
  生データ上の欠損率     0.0%   ← 値9が有効値として数えられている
  欠損コード処理後      16.9%   ← こちらが実態。多重補完の対象になる
```

この差は24変数で判定を変える。表示では両方を併記している。

## 設定はすべて config.py にある

変数名・リコーディングルール・閾値・パス・乱数シードは、すべて `src/config.py` に
集約されている。**分析コードに変数名や数値を直接書かない**という方針。

半年後に「この閾値どこで決まってる？」となったら、まず `config.py` を見れば足りる。

主なもの:

| 名前 | 中身 |
|---|---|
| `ACE_CATEGORIES` | ACEスコア8カテゴリの定義（主解析） |
| `COVARIATE_MISSING_CODES` | 共変量ごとの欠損コード対応表 |
| `ACE_SCORE_GROUPS` | 層別の区切り（0 / 1 / 2-3 / 4以上） |
| `MISSING_THRESHOLD_EXCLUDE` / `_IMPUTE` | 30% / 5% の閾値 |
| `WEIGHT_FINAL` | 分析で使うウェイト名（`_FINALWT`） |
| `RANDOM_SEED` | 42 |
| `ANALYSIS_DATA` / `SAMPLE_FLOW` | 出力先のパス |

## 過去に実際に起きた間違い

同じことを繰り返さないための記録。すべて修正済み。

| 何が起きたか | 影響 | 気づいた経緯 |
|---|---|---|
| `_AGEG5YR` の14を年齢カテゴリとして扱っていた | 年齢不明924人が最高齢層に | コードブックとの照合 |
| `_RACEGR3` の欠損コード9が未登録だった | 922人が第6の人種カテゴリに | 共変量の網羅チェック |
| 欠損率を生データで計算していた | 世帯収入が「欠損なし」に見えた | 実データでの検算 |
| `ACEPUNCH` を身体的虐待にも使っていた | ACEスコアが過大 | 変数定義の読み直し |
| 層別の上限が8に固定されていた | 10カテゴリ版で739人が欠損落ち | 定義変更時の検算 |
| `_MENT14D` の欠損コード9を未登録のまま追加した | 1,013人が「第4のカテゴリ」に | 追加直後の分布確認 |
| 3ファイルのレコード数を単純合計していた | 総回答者が579,105件（実際は457,670件） | サンプルフローの不自然な割合 |

共通しているのは、**エラーを出さずに静かに間違った値が出る**こと。だから実行が
通ったことは正しさの証明にならず、件数や分布を目で確認する必要がある。
